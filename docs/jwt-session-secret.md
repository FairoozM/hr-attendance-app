# Session signing key

## What was wrong

`backend/src/middleware/auth.js` resolved the session signing key like this:

```js
const JWT_SECRET = process.env.JWT_SECRET || 'hr-attendance-dev-secret-change-me'
```

`JWT_SECRET` was never set in production, so production signed and verified every session
with that string — a string committed to this repository. A key in source control is not a
key. Anyone with a copy of the source, or a lucky guess, could mint a token claiming
`role: 'admin'` and the API would accept it, because the only thing the middleware checks is
the signature and the signature was forgeable by design.

This was found on 2026-08-24 by minting exactly such a token during a post-deploy smoke test
and watching the production API accept it as an administrator.

## How it is resolved now

One module owns the key: `backend/src/config/jwtSecret.js`.

- **Production has no fallback.** With `NODE_ENV=production` and no `JWT_SECRET`, the process
  refuses to start. Refusing to boot is a loud, immediate, recoverable failure; booting with a
  public key is a silent, indefinite compromise.
- **The published keys are permanently barred.** `hr-attendance-dev-secret-change-me` and the
  development key are both on a deny list and are rejected in *every* environment, even if
  someone sets `JWT_SECRET` to one of them. Old tokens cannot be revived by reinstating the
  old value.
- **Short keys are refused**, minimum 32 characters, which rejects the hand-typed values that
  tend to appear when someone fills the variable in manually.
- **Signing and verification cannot diverge.** `getJwtSecret()` memoizes on first call, and
  both `authController.login` (signing) and `attachAuth` (verifying) go through it. There is
  no second place to read the key from and no way for the two halves of a request to disagree.
- **The key never reaches a log or a response.** No error message, property or stack contains
  it; failures name the variable and the remedy, never the value. There is a test that asserts
  this by trying each rejected value and searching the thrown error for it.
- **A misconfiguration is not an anonymous request.** `attachAuth` resolves the key outside
  the `catch` that handles bad tokens, so a configuration fault surfaces as a server error
  rather than quietly logging every user out.

Development and tests may set their own `JWT_SECRET`; with none set, non-production falls back
to a key named `hr-attendance-local-development-only-not-a-real-secret`, which production
rejects by name.

## Where the production key lives

| | |
|---|---|
| Secret | `hr-bi/production/jwt-secret` (resolve the ARN with `describe-secret`) |
| Readers | EC2 role `c2-hr-attendance-s3` only, inline policy `hr-bi-jwt-secret-read`, scoped to that one ARN |
| On the instance | `JWT_SECRET` in `/home/ubuntu/hr-attendance-app/backend/.env`, mode 600 |
| Generated by | `openssl rand -base64 64` (64 random bytes, 88 characters) |

The deploy tarball is built with `--exclude=.env` and extracted over the existing tree without
deleting, so the key survives deploys.

## Rotating it

Order matters. The application refuses to start without a usable key, so the key must be in
place *before* code that enforces that reaches the instance.

1. Generate and store: `openssl rand -base64 64`, straight into Secrets Manager over stdin.
2. Back up `.env` to a timestamped root-owned copy, then set `JWT_SECRET` from the secret,
   leaving every other line untouched.
3. Restart `hr-attendance-backend` and confirm `/api/health` returns 200.
4. Confirm a token signed with the old key now receives 401.

Rotation invalidates every existing session, by design: a token signed with the previous key
no longer verifies, so everyone signs in again. That is the point of the exercise, and it is
the expected user-visible effect.
